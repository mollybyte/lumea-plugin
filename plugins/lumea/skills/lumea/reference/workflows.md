# Процессы

Слэш-скиллы плагина — горячие клавиши к этим процессам; что показать, что спросить и в каком порядке — в `SKILL.md` каждого скилла, здесь не повторяется. Здесь только сквозное: модель кейса, порядок подтверждений, границы инструментов одной таблицей и куда какая заметка. Правила безопасности отправки реализует хук плагина (`hooks/hooks.json`: `PreToolUse` спрашивает подтверждение на каждую отправку, блокировку, действие во внешнем сервисе, создание и привязку issue, смену статуса пачкой, создание, правку и удаление быстрых ответов; `PostToolUse` напоминает о `failed` после массовых вызовов) — скиллы на него полагаются, а не переопределяют.

## Кейс

Кейс — единица работы с пластом тикетов: набор тикетов с одной проблемой, который ведёт разработчик или старший смены. Состояние живёт в Lumea, не в файлах плагина:

- **Тег** `case:<slug>` на каждом тикете (`slug` — латиница, цифры, дефис, до 32 символов). Обычный тег: виден команде в дашборде, переживает смену машины, оператор может снять его руками — это нормально. Все тикеты кейса — фильтр `tags: ['case:<slug>']` у `list_tickets`, `export_tickets`, `ticket_updates`; отдельного реестра кейсов нет, список — уникальные теги `case:*` из выгрузки.
- **Внутренняя заметка** в каждом тикете при открытии — по самой ранней заметке «Кейс … открыт» определяется дата открытия; заметка при добавлении тикета позже — другим текстом, чтобы дату не сдвигать. Тексты — в `/lumea:case`.
- **Файлы клиентов** — `.lumea/cases/<slug>/` в текущем рабочем каталоге; плагин не правит `.gitignore`, при первом создании папки об этом говорится один раз.
- Закрыть кейс — снять тег (`/lumea:case close`); закрыть тикеты — `/lumea:resolve`. Это разные действия и разные вопросы.

## Порядок подтверждений

Каждое пишущее действие — свой вопрос, «да» на одно не распространяется на следующее:

1. Рассылка (`bulk_send_messages`) — после таблицы «ref · клиент · язык · текст» целиком.
2. Закрытие (`bulk_update_tickets { status: 'closed' }`) — отдельный вопрос. Закрытие идёт по одному тикету через обычный поток: бот-шаблоны закрытия и CSAT-опроса, события, метрики — клиент может получить ещё и шаблонное сообщение, если оно настроено в проекте. `skipped` — уже закрытые, не ошибка.
3. Снятие тега кейса (`removeTags`) — ещё один вопрос.

Правило (сколько подтверждений, что показать до вызова) и тексты ошибок — в `SKILL.md` справочника, разделы «Правила» и «Лимиты». Читающая часть sweep и группировки может идти в форке агентом `analyst` (без пишущих инструментов); пишущая — всегда в основном разговоре после «да».

## Сбор логов

Один запрос каждому клиенту кейса на его языке под его платформу — после таблицы «клиент → текст» и «да». Язык и платформа — из переписки, структурированного поля нет; кому нужное уже прислано — не спрашивать повторно. Кто ответил и файлы — `ticket_updates` по тегу кейса и `get_message_media`; фоновое ожидание — `/lumea:watch case <slug>`. Шаги, именование файлов и три формы ответа `get_message_media` — `/lumea:collect`.

## Resolve

Адресаты — тикеты кейса (`list_tickets { tags }`) или тикеты issue (`list_issue_tickets { projectName, iid }`), закрытые в рассылку не включать. Дальше — «Порядок подтверждений» выше. Шаги — `/lumea:resolve <slug | #iid> [суть фикса]`.

## Sweep

Правило на естественном языке → выборка `export_tickets` с фильтрами (`status`, `projectName`, `channel`, `priority`, `tags`); условия по датам и «кто писал последним» — локально по выгрузке. До выполнения — таблица выборки (до 50 строк, остальное числом) и **точное** действие: инструмент, поле, значение, число тикетов; неоднозначное правило — вопрос, не догадка. Без явного правила закрытия ничего не закрывать: «зависло» — показать. Шаги — `/lumea:sweep <правило>`.

## Issue из кейса

Головной тикет — самый содержательный; `find_related_issues` для него → кандидаты с вердиктами `duplicate` / `related` → выбор пользователя → `create_issue_from_ticket` или `link_issue` к существующему, остальные тикеты кейса — `link_issue { ticketId, iid }`. Тег `issue#<iid>` появляется на тикетах сам; `unlink_issue` берёт `linkId` (поле `id` из `list_ticket_issues`), не номер. Все тикеты issue потом — `list_issue_tickets`. Шаги — `/lumea:issue <slug | тикет> [#iid]`.

## Быстрые ответы

Шаблоны, которые уходят клиентам от операторов и AI: правка меняет то, что клиенты получат уже сегодня, поэтому `update_quick_reply`/`create_quick_reply`/`delete_quick_reply` — только после показа итогового текста целиком (для правки — с diff) и «да»; область (проект или глобально) называть явно. Шаги — `/lumea:replies`.

## Рассылки

Рассылка (`broadcasts`) — не то же самое, что `bulk_send_messages`: она шлёт один шаблон бота по выборке тикетов, работает фоном воркером, переживает обрыв соединения и хранит результат по каждому получателю. `bulk_send_messages` — для разных текстов в десятки тикетов здесь и сейчас; рассылка — для одного текста в сотни, с отслеживанием.

Порядок обязателен, шаги не пропускать:

1. `preview_broadcast { statuses, projectName?, channels?, since?, until? }` — сколько тикетов попадёт и примеры. **Ничего не создаёт.** `overLimit: true` — больше потолка MCP (2000), сузить фильтры или отдать кампанию человеку в дашборде.
2. Показать пользователю: число получателей, фильтры словами, название и **текст шаблона целиком** (`list_bot_templates` даёт `body` с переменными `{client_name}`, `{ticket_id}`, `{project_name}`), закрывать ли тикеты после отправки. Спросить «да».
3. `create_broadcast { name, templateId, maxRecipients, statuses, … }` — `maxRecipients` ставить равным числу из предпросмотра с небольшим запасом: выборка растёт на ходу, и кампания, которая между предпросмотром и созданием распухла, не должна уйти молча. **Создание не отправляет ничего**, отвечает `started: false`.
4. `start_broadcast { broadcastId }` — **отдельный вопрос и отдельное «да»**. С этого момента сообщения уходят клиентам.
5. Ход — `get_broadcast { broadcastId }`: `progress` с `sent`, `failed`, `pending`, `lastActivityAt`. Не опрашивать чаще раза в 10–15 секунд.
6. Упавшие — `list_broadcast_jobs { broadcastId, status: 'failed' }`: причина лежит в `error` у каждого джоба. Одинаковая ошибка у всех (например «бот заблокирован») означает, что повтор упадёт так же — сказать это, а не повторять. `retry_broadcast` — только после разбора и ещё одного «да».

Остановить идущую — `cancel_broadcast` (воркер выйдет на ближайшем джобе; уже отправленное не отзывается), продолжить с того же места — `resume_broadcast`. Повторная отправка одному тикету невозможна по устройству: на каждый тикет кампании заведён ровно один джоб, и `sent` в очередь не возвращается.

Фильтры у созданной рассылки заморожены: поменять выборку нельзя, только отменить и создать новую.

## Ошибки и права

Тексты 401/403/429 и что на них отвечать — правило 5 в `SKILL.md` справочника; права по скиллам — таблица в `/lumea:setup`. Одно сверх того: 500 «Сервер настроен неверно» — на сервере не задан секрет, новый ключ не поможет, нужен администратор.
