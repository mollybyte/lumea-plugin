# Сбор данных у клиентов кейса

Аргументы: `$ARGUMENTS`. Процесс — `${CLAUDE_PLUGIN_ROOT}/skills/lumea/reference/workflows.md`, раздел «Сбор логов».

## `<slug> <что нужно>`

1. `list_tickets { tags: ['case:<slug>'], perPage: 100 }` (`hasMore: true` → повторить с `page: 2` и дальше, пока не `false`); пусто — сказать и остановиться.
2. Для каждого тикета `get_ticket_messages { ticketId, limit: 30 }` (последние 20–30 сообщений; не полный `get_ticket_context` — тикетов в кейсе может быть под сотню, а он тяжелее): язык клиента, платформа и версия, что уже присылал — всё из текста переписки, отдельного структурированного поля нет. У кого нужное уже есть — не спрашивать повторно, отметить в таблице.
3. Текст запроса для каждого: конкретно (путь к файлу, команда, что скриншотить), коротко, на языке клиента, с учётом платформы (`~/Library/…` для macOS, `%APPDATA%` для Windows и т. п.). Никаких обещаний сроков.
4. Показать таблицу «ref · клиент · платформа · текст» и вопрос: «Отправить N клиентам?» — ждать «да». Хук плагина покажет подтверждение ещё раз — это нормально.
5. `bulk_send_messages { items: [{ ticketId, content }] }`; при `nextIndex` — продолжить с него (`items.slice(nextIndex)`). Отчёт: `sent`, `failed` поштучно с причиной.
6. Предложить `/lumea:watch case <slug>`.

## `status <slug>`

`ticket_updates.since` не бывает старше 7 дней от текущего момента: `since = max(<время отправки запроса>, сейчас − 6 дней)`; если время отправки неизвестно — по умолчанию «6 дней назад». Более старые события `ticket_updates` не покажет — для них `get_ticket_messages` по конкретному тикету. `ticket_updates { since, tags: ['case:<slug>'], limit: 100 }` (при `truncated: true` — ещё раз с `nextSince`) → таблица по `ticketRef`, `client`: ответил (есть событие `kind: 'client_message'`), файлы (`attachment.fileName`, `attachment.fileSize`). Кто не ответил — предложить напомнить (снова через подтверждение).

## `fetch <slug>`

1. `status`, затем для каждого события с `attachment` — `get_message_media { messageId }` (`messageId` есть в каждом событии `client_message`). Если `status` вернул `truncated: true` — продолжить с `nextSince`, пока не `false`.
2. По форме ответа `get_message_media` — три случая:
   - текст ≤ 200 КБ (`structuredContent.inline: true`, контент текстовый) — сохранить как есть в `.lumea/cases/<slug>/<ticketRef без #>-<fileName>` через `Write`;
   - картинка ≤ 5 МБ (`inline: true`, контент — изображение) — байты не сохранять, описать содержимое в `<ticketRef>-<fileName>.md`;
   - больше лимита или бинарный файл (`inline: false`, контент — текстовая заметка со ссылкой на CRM) — сохранить `<ticketRef>-<fileName>.md` с этой заметкой и пометкой «больше лимита, скачать через CRM: <ссылка из ответа>»; если файл нужен целиком, его можно скачать тем же ключом из окружения: `curl -H "Authorization: Bearer $LUMEA_ACCESS_KEY" $LUMEA_URL/api/media/<messageId> -o <файл>` (ссылка из ответа — тот же адрес);
   - ошибка вызова `get_message_media` — вложение пропустить, отметить в итоге какое и почему.

   `attachment.fileName` в событии бывает `null` (не всегда сохранено) — тогда вместо имени файла в пути использовать `messageId`.

3. При первом создании `.lumea/` сказать: «Папка `.lumea/` в `.gitignore` не добавлена — добавьте сами, если это репозиторий».
4. Итог: список файлов и по одной строке, что в каждом (ошибки, версии, время сбоя).
