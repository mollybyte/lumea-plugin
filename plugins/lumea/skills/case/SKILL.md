# Кейс

Аргументы: `$ARGUMENTS` — подкоманда и параметры. Процесс целиком — в `${CLAUDE_PLUGIN_ROOT}/skills/lumea/reference/workflows.md`, раздел «Кейс»; здесь — что показывать и что спрашивать.

**Slug**: латиница, цифры, дефис, до 32 символов; иначе предложить исправленный и спросить.

**Тикеты**: ref — короткий id, полный uuid или ссылка на тикет. Из ссылки и полного uuid брать id прямо из строки, поиск не нужен; короткий id разрешать через `search` до полного uuid. Нераспознанные перечислить и не включать.

**`bulk_update_tickets`**: за один вызов — ровно одно поле кроме `ticketIds` (здесь всегда `addTags` либо `removeTags`, никогда оба и никогда вместе со `status`/`priority`). Возвращает `{ done, failed: [{ ticketId, error }], skipped }` и, если сработал бюджет времени, `nextIndex` — тогда повторить вызов с оставшимися `ticketIds` (`ticketIds.slice(nextIndex)`), как у `bulk_send_messages`.

## open

1. Таблица кандидатов: ref, проект, клиент, заголовок, статус.
2. Вопрос: «Пометить N тикетов тегом `case:<slug>`?» — ждать «да».
3. `bulk_update_tickets { ticketIds, addTags: ['case:<slug>'] }` (с продолжением по `nextIndex`), затем `add_internal_note { ticketId, content }` в каждый успешно помеченный: `Кейс case:<slug> открыт, ведёт <имя из whoami>. <одна строка о проблеме из заголовков>`. `whoami` вызвать один раз.
4. Отчёт: помечено `done`, `failed` поштучно с причиной. Напомнить: `/lumea:collect <slug> …` для сбора логов, `/lumea:watch case <slug>` для уведомлений.

## add

Как `open`, с `addTags`. После успешной пометки — внутренняя заметка, но своим текстом (не как у `open`, иначе `show` примет её за дату открытия кейса): `Тикет добавлен в кейс case:<slug>, ведёт <имя из whoami>.`

## remove

Как `open`, с `removeTags`; без внутренней заметки. Свой вопрос подтверждения: «Убрать N тикетов из кейса `case:<slug>`?» — ждать «да».

## show

1. `list_tickets { tags: ['case:<slug>'], includeClosed: true, perPage: 100, sort: 'desc' }` (`hasMore: true` → повторить с `page: 2` и дальше, пока не `false`) → таблица: ref, клиент, статус, последнее сообщение (`lastMessageAt`; ответа не содержит поле «от кого» — если нужно показать, выводить по статусу: `unanswered` → последним писал клиент, иначе — сотрудник или бот), issue (`tags` вида `issue#N`). «Без ответа сейчас» — число тикетов со `status: 'unanswered'` в этом же ответе.
2. Дата открытия — самая ранняя заметка «Кейс … открыт» (искать через `get_ticket_context` по первым 2–3 тикетам из списка выше, не только по первому — заметка могла достаться не самому свежему по `lastMessageAt`; если нигде не нашлась — считать открытием 6 дней назад). `ticket_updates.since` не бывает старше 7 дней от текущего момента: передавать `since = max(<дата открытия>, сейчас − 6 дней)`; если дата открытия старше — сказать, что события до `since` `ticket_updates` не покажет, для них — `get_ticket_messages` по конкретному тикету. `ticket_updates { since, tags: ['case:<slug>'] }` (при `truncated: true` — продолжить с `nextSince`) → «с открытия: M сообщений от клиентов, K с файлами».
3. Пустой список — «кейса `<slug>` нет», предложить `list`.

## list

`export_tickets { limit: 200, includeClosed: true }`, продолжая по `nextCursor` до 5 страниц (та же причина, что в `groups`: ответ MCP ограничен по объёму, 1000 строк за раз не пройдёт) → собрать все теги вида `case:*` из строк → таблица: slug, тикетов, без ответа (по `status`), последняя активность (максимум `lastMessage` в группе). Если после 5-й страницы `nextCursor` всё ещё не `null` — предупредить: «смотрели 1000 самых активных тикетов, кейс с тихими тикетами сюда не попадёт — `show <slug>` покажет его целиком».

## close

Показать тикеты кейса, спросить «снять тег `case:<slug>` с N тикетов?», после «да» — `bulk_update_tickets { ticketIds, removeTags: ['case:<slug>'] }` (с продолжением по `nextIndex`). Тикеты не закрывать — для этого `/lumea:resolve`.
